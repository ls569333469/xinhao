# 1022｜持续追踪主站页面接入与数据同步方案 v1.0

日期：2026-10-20。状态：用户已批准实施；布局采用方案①及本页“持续追踪／历史信号”双子标签，发布与实际验收记录见第10节。2026-10-20已补充接口、真实数据及跨页面布局复核（第8.1—8.3节）。

承接：[1017｜ABC持续追踪规则](1017-ABC持续追踪与C接入-最终执行与审计方案.md)、[1021｜EMA金叉弱中强统一分级](1021-EMA金叉弱中强统一分级与列表简化方案.md)。本文负责主站新增页面及追踪续接，不重新制定金叉等级或ABC资格。

## 1. 本次要交付什么

主站增加一个“持续追踪”页面，让用户用熟悉的行情列表查看已经出现过信号的代币、后续走势和检查进度。进入页面自动显示已有记录，不再要求先点击“载入观察记录”。

列表成员由持久化事件及追踪会话决定。某币本根没有新金叉，但原观察仍有效，就应继续出现在追踪中；已经结束的记录进入历史，保留原始触发和结束原因。

交付包含页面与后台真实续接。仅迁移列表、只显示“观察中”或刷新行情价格，不算持续追踪上线。

## 2. 用户已确定的界面边界

1. 采用预览①“主站同款列表”的信息组织方式，正式页面直接复用现有主站外壳和组件。
2. 只新增页面及进入它的最小必要导航入口；优先复用、接通已有入口，不重复加入口。
3. 不改原市场扫描、投研、设置页面的内容、布局、颜色、字体、侧栏、筛选条件和既有交互。
4. 预览版自行设计的左侧栏、顶部导航、配色及控件样式不迁入正式主站；预览只用于确认列表布局。
5. 不调整金叉弱观察／弱／中／强或组合筛选，不把多头排列持续标成一次新的金叉。
6. 不新增一套调度设置，不改变现有1H／4H计划和自动补齐开关，不增加自动交易功能。

新页面自身需要的状态和来源筛选放在其内容区，使用现有控件样式。新增样式限定在新页面容器，禁止覆盖全站选择器。浏览器列配置、筛选及布局存储使用独立命名空间，避免污染主站原设置。

## 3. 现状与需要解决的问题

| 现状 | 本方案处理 |
|---|---|
| 原独立 `/tracking/` 页面偏工程展示，需要手动载入 | 在主站内自动读取，默认展示行情列表 |
| 用户从主站难以发现追踪功能 | 使用现有导航体系提供明确入口，可返回主站原页面 |
| 当前信号与历史观察容易混淆 | 原始触发、当前走势、追踪状态分列 |
| 行情更新不代表观察已处理新K线 | 明确显示行情时点和追踪检查截至 |
| 本根没有新金叉，不能据此隐藏旧事件 | 用事件账本决定成员，行情只用于补充展示 |
| 新技术交叉与旧A观察profile未必一一对应 | 建立覆盖映射，未具备规则的如实显示，不冒充已追踪 |

JCT取证样例：此前读取的快照中，2026-10-20 12:00闭合4H根出现EMA7同时上穿EMA25与EMA99，1021技术分级为强；16:00行情已到，而既有观察会话仍只检查至12:00，状态为 `observing`。原A资格还存在 `cross_precedes_candidate_qualification` 阻塞。

这些是讨论期间的历史快照，不代表当前实时状态。它说明：技术信号存在、完整策略资格、观察是否跟上，是三个独立问题。实施时应重新取证，不能直接把旧样例时点写入生产逻辑。

## 4. 页面位置与交互

### 4.1 页面结构

在正式主站现有页面切换体系内新增“持续追踪”。沿用主站外壳、导航、表格、涨跌颜色、字号、密度和详情容器，具体路由遵循现有实现，不另造一套站点。

页面内容自上而下：持续追踪／历史信号子标签、搜索与状态／来源／触发日期筛选、数据状态说明及主站同款列表。默认不摆放导出、修订统计、恢复任务、技术水位等大板块；必要技术信息放入详情折叠区。原工程页和底层能力保留，避免删除已有接口或历史。

### 4.2 默认范围与筛选

- 默认显示“追踪中＋待补数据”，切换可看“已结束”及“全部历史”。
- 支持按币名／合约搜索、A／B／C来源、市场筛选；使用现有市场标识。
- 每个完整 `market + symbol` 一行；同名不同市场分行，不按显示简称合并。
- 同一合约多条观察聚合为一行，显示“进行中N条”；进入详情按事件逐条查看。
- 有任一活动会话的合约留在默认列表；仅有结束会话的进入历史。部分会话待补时标“部分待补”，不能掩盖其他会话状态。
- 搜索无结果、确实无记录、接口读取失败分别提示，失败不得展示成“历史为空”。

### 4.3 点击代币与历史

点击币名使用主站既有详情交互，查看该合约的事件列表。默认聚焦当前行对应的活动事件；用户可以切换其他事件及已结束历史。

详情展示原始触发K线、具体交叉或ABC来源、触发时等级、原始资格、后续逐根进展、检查截至、缺数原因和结束原因。版本、修订、来源证据等折叠展示。加载失败保留列表及已读详情，并提供重试，不让底部长期停留在“正在读取完整数据”。

## 5. 列表字段与时间口径

以下为首版默认字段，列宽、排版、颜色沿用正式表格。主站已有行情列优先复用，不另计算同名不同口径的数据。

| 字段 | 展示与口径 |
|---|---|
| 代币／市场 | 完整身份关联，币名可点开详情 |
| 当前价格、24H涨跌、量能 | 主站已有行情口径；无行情显示“暂无”，保留追踪行 |
| 触发信号 | 例如“4H EMA7↑EMA99”，不能只写一个“金叉” |
| 触发等级 | 使用该事件保存的规则版本与等级，不用当前排列覆盖历史 |
| 触发时间 | 原始信号闭合时间，明确1H或4H；北京时间展示 |
| 触发后表现 | 相对该事件触发闭合价的价格变化；缺基准时不计算 |
| 当前走势 | 显示当前已知排列／走势，与原始触发分开 |
| 追踪状态 | 追踪中、待补数据、已结束；混合会话显示数量和部分待补 |
| 检查截至 | 该会话连续完成评价的闭合K线时间，不用刷新时间代替 |

同币多事件时，默认行选“最近的活动事件”为表现基准，并明确其触发时间；无活动事件时选最近结束事件。其他事件的不同收益基准在详情分别展示，不将多个事件拼成一笔表现。行内检查截至按当前代表事件展示，混合状态须提示还有其他事件及其进度。

“触发后表现”只是观察统计，不是成交收益。未闭合的实时价格可以展示，但必须沿用行情时点标识，不用它结束闭合K线追踪。历史补登记分别保存信号发生时间和系统发现时间，不伪称实时发现。

## 6. 数据同步：采集到页面的完整链路

### 6.1 事件登记与既有记录接入

以持久化追踪账本为主数据源，保留事件ID、会话ID、市场、合约、策略／技术类型、周期、规则版本、原始触发根、发现时间和输入版本。

先接入既有ABC会话，包括JCT已有记录。重复扫描或刷新不得重建同一事件；新触发另建事件，不能覆盖旧事件或复活人工结束的会话。已归档技术事件的补登记有明确时间范围和进度，不扫描一次近60根就宣称完整历史已经恢复。

### 6.2 已有活动会话必须独立续接

既有1H／4H采集归档后，复用共享处理通道，按持久化游标续接活动会话。需要分别检查“发现新事件”和“推进旧会话”两条路径；即使本根没有新信号，也必须评价已有会话。

源采集周期、事件周期和观察评价周期分别绑定。B的1H触发及确认仍按原规则处理，其后续4H观察按既有profile推进；不能因来源叫1H就把所有追踪改成1H。

### 6.3 连续逐根处理与缺口恢复

从上次连续评价水位后的第一根开始，按真实闭合根顺序处理到固定目标。中间缺根或所需字段不足时登记缺口并显示待补，不跨过去判断走势仍有效或已经结束。

自动补齐沿用现有共享worker、有界队列、限流和重试；不新增独立采集循环。补齐后从最早受影响根重放，不能只计算最新一根而漏掉途中曾经破坏的结构。来源权限、402、429／418及历史不可得保留具体原因，不用当前值代替历史值。

事件、修订和连续水位按既有事务契约落盘；跨库处理通过幂等消费及ACK续接。重启后从持久进度恢复，来源修订保留旧结果和修订记录，不覆盖原始触发事实。

### 6.4 发布一致的列表读取版本

复用现有追踪读取视图和行情摘要，在服务端形成可标识的列表投影。返回追踪版本、行情版本、各自时点、完整性和分页信息；完整生成后发布，不让前端任意拼接不同版本的数据。

行情可以比追踪更新，但应显示“行情截至16:00／追踪检查至12:00，处理中或待补”等真实状态。调度心跳、commit_seq增长和 `observing` 字样均不能代替连续根已完成的证据。

如果分页过程中版本改变，应继续固定版本或重新读取一致版本，避免重复行和漏行。刷新数据不删除追踪成员；合约行情暂缺或退市数据不可得时仍保留历史及原因，不自行新增结束规则。

### 6.5 页面自动读取与稳定显示

进入页面自动读取已保存数据，重新激活时检查。页面可见时使用后台提交通知唤醒的长连接（最多等待50秒后保活），或手动刷新；不再采用每30秒固定检查。隐藏或离开页面时取消本页连接。保活不发起行情扫描或补采。

无新版本不重绘；新版本完整读取并校验后替换，保留搜索、筛选、排序、滚动、选中合约及展开事件。请求失败保留上次成功数据并标明陈旧；初次失败明确显示错误及重试。并发响应使用代次校验，旧响应不得覆盖新筛选结果。

前端读取不触发扫描、补采、模型或交易。若现有读取视图需要创建固定快照，须限定为只生成展示视图的既有操作，不得串入业务采集；不能把“需手动创建视图”继续留给用户。

## 7. 持续多久、什么时候结束

继承1017第4.2节的既有profile，不设16小时／一周自动清除期限。缺数属于待补，完整策略资格未通过与技术观察可分开；结束的事件仍可在历史查看。

| 既有观察类型 | 结束与保留规则 |
|---|---|
| 原A强观察 | 闭合4H不再满足EMA7＞EMA25＞EMA99时结束，相等算破坏 |
| 原A中观察 | 闭合4H不再同时满足EMA7＞EMA25且close＞EMA99时结束 |
| B观察 | 后续闭合4H EMA7≤EMA25结束；上涨超过3%不结束，当前LSR不改历史资格 |
| B风险线 | 固定S0跌破先提示，不另加自动结束或卖出条件 |
| C确认后 | 固定T0—C1真实根最低low，后续闭合收盘严格跌破才结束，等于不结束 |
| C未确认到期后 | 原expired保留；技术观察以固定T0 low严格跌破结束，窗口外反弹不补成窗口内确认 |
| C等待期失效 | 结束对应周期，新周期按原规则重新武装 |
| 人工结束 | 自动重放不复活，真正的新触发另建事件 |

### 7.1 1021技术等级与原A观察profile的覆盖缺口

1021的“弱观察／弱／中／强”是技术交叉强度，不等于1017原A强／中观察profile或完整策略资格。例如7穿99后EMA7仍低于EMA25，就不能直接套原A中的“EMA7＞EMA25”持续条件。

| 记录类型 | 首版接入方式 |
|---|---|
| 已有ABC会话及明确profile | 原样接入并修复实际续接，不改等级、资格或结束规则 |
| 已保存技术交叉且能关联已有会话 | 关联展示原技术事件及独立会话状态，不覆盖任一口径 |
| 技术交叉存在，但尚无匹配profile／会话 | 历史详情如实显示“技术事件，观察规则待明确”；不伪装成持续追踪中 |
| 尚未持久化的旧技术交叉 | 有界回填，记录历史发生和补登记时间；缺数据标待补，不猜测 |

实施前需补齐7穿25、7穿99、25穿99及同时交叉的“事件类型→已批准profile／覆盖缺口”映射。所有新技术类型的长期观察结束条件如需新增，应单独列入本方案增补供审阅，不在页面迁移中暗自引入。既有ABC追踪接入可先完成，但不能据此宣称所有新金叉类型都已长期追踪。

预计核对位置包括 `design/unified-workbench-fragment.html`、`design/unified-workbench.js`、`tracking/ui/`、`tracking/a_pipeline.py`、`tracking/observer.py`、`tracking/runtime.py` 和相关接口。文件是否实际修改以最小实现为准；不得借此重做主站或批量迁移样式。

执行顺序：

4. 对可恢复的历史做有界、幂等接入；无法恢复的范围逐项说明，不伪造历史。
5. 完成下列验证后发布，交由用户点验。发布前做一致备份；回退只回退代码和兼容配置，不用旧数据库覆盖发布后的新行情或追踪事件。

### 8.2 数据读取适配的实施约束

**新增主站专用读取适配，保留旧工程页和旧API契约。** 下列 `/api/tracking/workbench/*` 为拟新增路径，当前尚不存在；实际命名在实施时固定，不冒称现有能力。

| 拟新增读取能力 | 需要解决的具体问题 |
|---|---|
| GET版本状态 | 返回轻量的行情generation、tracking/recovery版本和展示时点；版本通知不全量读历史或反复计算全文件hash |
| GET合约列表 | 在服务端按完整market/symbol聚合，先筛选及汇总再按合约分页；一页最多100合约，返回稳定cursor和完整性信息 |
| GET合约事件／事件详情 | 按合约或event_id有界加载事件、修订、时间线与缺口；不得为588行逐行拉取完整历史 |

已有 `TrackingReadAPI` 支持 `observation_status=active`，包含observing及paused_awaiting_data，可复用语义。旧 `history=history/forward` 区分历史补算与前向发现，**不是“已结束／全部历史”状态**；全部历史通过不加观察状态过滤实现，不能传未经支持的 `history=all`。

旧 `/events` 是事件分页，上限100，symbol是精确匹配。新列表不能只拉第一页再按币去重，也不能在当前页上做搜索就宣称全局搜索。必须在服务端完成合约成员、匹配范围、活动／待补计数及代表事件选择；搜索资产简称时沿用可信身份目录，不按币名猜合约。

读取版本需单独适配：旧read_view仅在进程内保存，最多256个；tracking或recovery提交变化会返回409 stale，重启或淘汰后返回410 unknown。它不支持跨任意后续提交长期读取同一冻结版本。主站新投影应在短只读事务内生成有界、不可变展示结果并缓存，以token绑定筛选、排序、行情与追踪版本；后续分页使用同一结果。缓存受条数、字节及有效期约束，过期返回明确错误，前端有界重取并保留旧表，不无限重试、不改旧接口的失败保护。

行情与追踪分属不同存储，不能宣称跨库事务原子性。生成前后分别核对来源版本，变化时最多重取2次；仍变化则保留已成功版本并标“更新中”。缓存的是生成时读取的结果，不是token加实时查询。列表翻页及详情更新都要校验版本；点击已不属于当前筛选的事件仍可按明确事件身份查历史，不偷偷替换成另一次事件。

### 8.3 页面布局隔离的实施约束

源码确认主站通过 `page(p)`切换 `[data-view]`，正式统一表格挂载到市场页中的 `#unifiedWorkbench`。现有全局CSS会调整 `.layout`、`.sidebar`，部分规则取决于市场页是否可见。现有fragment里虽有ABC追踪链接，其 `.brandbar`又被CSS隐藏，不能以“HTML里有链接”证明用户能看见入口。

1. **样式隔离。** 不引入旧 `tracking/ui/styles.css` 或预览CSS；它们包含 `:root`、body、button、table等全局规则。复用正式主站现有变量；必要的列表排版规则只对 `#trackingWorkbench`生效，取现有值，不重设计配色。禁止改动既有全局CSS或扩展其选择器影响范围。
2. **壳层条件。** 主站已有只在market可见时隐藏topline/banner等规则，新页不能通过强制显示market或修改旧全局规则模仿。新页如需同等效果，只在tracking可见条件下附加独立规则；离开时自动恢复，不改变其他页的计算样式。
3. **脚本隔离。** 主站存在全局点击代理，尤其 `[data-detail]`会被旧逻辑作为数字下标处理。新控件使用独立 `data-tracking-*`属性及局部事件绑定；除必要导航外，不复用data-detail、data-tab、data-result等行为属性，不加载旧app.js，不覆盖window.renderMarket或UnifiedWorkbench。
4. **详情隔离。** 复用现有详情的视觉规范，不直接抢占旧drawer DOM及其ID。新增容器内独立详情，限定Escape、焦点锁及遮罩处理；关闭时还原焦点和滚动，切换到其他页时清理本页事件与弹层。
5. **状态隔离。** tracking独立保存筛选／列配置；不改 `unified-last-query-v33r5`等市场存储、不操作selectedTokens，不触发投研选币通知。首次打开再初始化，防重复监听；退出页面暂停本页通知连接并取消未完成请求。
6. **导航与窄屏。** 只补必要入口，不重排已有导航或改原标签。用原生页面切换保证前后返回与当前页标识一致；在现有断点验证导航换行、横向表格滚动、详情遮罩与键盘操作，不为缩窄新表去压缩主站列宽。

本轮属于设计与静态代码复核，尚无新正式页面，因而不能声称已经实测“零布局影响”。上述边界进入实施白名单与下面的回归标准；只有代码落地后的跨页对照通过，才能确认实际隔离效果。
