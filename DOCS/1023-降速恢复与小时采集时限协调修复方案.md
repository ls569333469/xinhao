## 1. 结论与修复目标

已确认：币安限流后的降速只会加重、不会自动恢复，与固定 30 分钟采集时限不匹配，是本次持续采集变慢及多轮快照无法更新的直接原因之一。还存在两个小时任务共用串行采集通道、每个却各有 30 分钟预算的结构问题。

建议实施一套完整修复：**限流按事件处理、冷却后逐步恢复、等待受截止时间约束、两个任务共用小时预算、可复用的已收盘数据增量采集**。不能只重启清空降速状态、把时限改成 80 分钟，或降低数据完整性门槛。

实施目标：在供应商正常、证据可用时恢复每小时更新；供应商封禁或证据缺失时保留最后合格数据，并明确展示阻塞及待补范围。持续追踪、主站信号规则与弱中强分级均不因这次修复改变。

## 2. 已核实的问题及证据边界

### 2.1 降速状态一直保留

`request_pacer.py` 的 `rate_limited()` 对每条 418/429 都执行 `_interval *= 2`；没有成功后的恢复方法。

| 项目 | 已核实行为 |
|---|---|
| 币安初始派发间隔 | `RequestPacer(480, 1)`，即 0.125 秒；这是项目限速参数，不是币安官方允许配额 |
| 4 条 418 后 | 0.125 → 0.25 → 0.5 → 1 → 2 秒 |
| 后续成功 | 不降低间隔；同进程的市场扫描、B1H、补齐继续共用降速状态 |
| 实际样本 | B 任务 641 次请求全部 200；最近 100 次响应耗时中位数约 271ms，派发间隔中位数约 2 秒 |

10 月 20 日 22:04 的前三条 418 来自已发出的同一批在途请求，不能据此认定三次独立封禁；但代码仍连续降速三次。22:10 又出现一条 418，进一步降至 2 秒。

冷却本身有执行：日志显示分别等了约 360 秒、386 秒后才恢复派发。因此本次不能归结为“冷却完全失效、封禁中不停重试”。真正缺的是事件合并、冷却后的恢复和与任务预算协调。

### 2.2 30 分钟时限不能容纳降速后的请求量

市场一轮约需 2,400 次请求时，2 秒一次，仅派发排队就需要约 80 分钟，尚未计入封禁冷却、网络、重试与本地计算。它和 1,800 秒时限明显不兼容。

|---|---|
| 10 月 20 日 21 点市场 | 前置接口 4 次尝试中 3 次超时；这是网络/上游超时，不能全部算成降速问题 |
| 22 点市场 | 858 次尝试、4 条 418；关键字段覆盖约 34%～35%，未通过发布门槛 |
| 23 点市场 | 838 次尝试；未见本轮 418，但仍低速，关键覆盖约 34% |
| 10 月 21 日 0 点市场 | 747 次尝试，741 次 200；关键覆盖约 31%，还剩 5,253 次请求额度，主要耗尽的是时间 |
| 23 点 B1H | 585 次尝试全部 200，实际仅评估 145/587；442 份因时限失败 |

最后一份合格主站快照于 10 月 20 日 20:09:54 可用。失败轮保留旧快照符合现有发布保护，不应通过写入残缺新快照来制造“已更新”。

### 2.3 当前时限只限制发新请求，不完整限制任务生命周期

`request_gate.py` 在请求前判断截止时间；`scanner.py` 默认 `pacer.wait(max_wait=None)`，等待后才再次检查。长冷却可能占住采集通道，过期后本地计算、逐币失败收尾也可能继续运行。

市场与 B1H 都在整点后 120 秒触发，共用一个数据 worker，任务内部才有多线程。两个任务各 30 分钟，串行相加已用满一小时，尚无收尾和历史补齐余量。

### 2.4 已排查但不能误判的事项

- 已查 136 个数据任务、3,501 次恢复尝试和 116,073 条币安遥测，未发现跨数据任务请求重叠。不是已有证据支持的“两任务同时抢采”。
- 4H 有个别合约尚未追上，但当前 B 样本的 157 次 4H 请求对应 157 个合约，没有看到同币不断重拉 4H 的循环。4H 缺口不是本次全局 2 秒降速的解释。
- 新 1H 写入按时间键追加、同键修订保留；自动清理关闭。没有“每补新一小时便删掉旧一小时”的逻辑。不通过删除历史解决降速。
- 1022 上线时间与故障相邻，但发布前后 `request_pacer.py`、`scanner.py` 等采集核心文件哈希相同，未发现此次页面上线增加币安请求的代码证据。不能把时间相邻当作因果证明。
- 418 表示 IP 自动封禁；原始触发的具体配额仍未知。旧日志没有保存用量头及错误正文，也未看到此前 429；不能排除共享出口其他流量，更不能声称已查明某个官方权重上限。

## 3. 第一部分：修复限流和降速恢复

### 3.1 保留全局共享约束，按供应商及官方限额作用域管理

所有币安访问入口使用同一协调器：市场、B1H、补齐、证据修复及对应 transport。保留单数据通道；不能给不同任务各建一个独立额度池。CoinGecko 保留自己的限速与冷却。

币安不同 API 产品/路径按其官方限额作用域分别核算；共享 IP 的封禁保护覆盖相关调用，不把所有接口配额简单混成一个数值。实施前核对实际使用的 futures 接口官方权重规则及响应头，不能套用 Spot 的具体额度。

除派发次数外，按 endpoint、参数和窗口计入请求权重；尤其区分 `klines limit=1500/1000` 与轻量接口。未知权重不能记为零：使用经审阅的保守配置；无法确定有效上限时暂停提速并报告原因，不能自动套用 8 次/秒。

### 3.2 同一批在途限流只计算一次降速事件

每次派发携带 `dispatch_generation`，响应关联 task、request、generation 和限流事件。

1. 正常状态下首条 429/418 打开事件、阻止新派发，更新 `blocked_until`。
2. 已经在途且属于该事件前派发批次的后续 429/418，仅延长冷却至所有有效 Retry-After 的最晚时间，不再重复乘二。
3. 冷却后的受控试探若再次限流，属于新的失败事件，应重新冷却、降低速度；不能因旧事件未清理而忽略。
4. 不同错误码或更长封禁证据允许升级事件严重性；事件去重不能缩短供应商要求的冷却。

### 3.3 429 与 418 分开处理

| 情况 | 拟议行为 |
|---|---|
| 429 | 停止该作用域新派发，遵守 Retry-After，降低下一次恢复速度 |
| 418 | 打开封禁状态，禁止新请求直到封禁期结束；只允许一个恢复试探名额 |
| 已在途请求 | 接收结果、保存遥测和已取得的证据；不强行当作新重试 |
| Retry-After 缺失或格式错误 | 暂定兜底：429 至少 60 秒，418 至少 15 分钟；这是本项目保护参数，不是官方封禁时长；若错误正文提供更晚有效解禁时间，取更晚者 |
| 冷却超过任务剩余预算 | 当前任务保存断点、让出通道，标记“供应商冷却”；不原地等待到下一小时 |

解析 Retry-After 的秒数/HTTP 日期格式；从收到响应时计算，并保留小幅时间余量。记录必要状态到运行态文件，重启不能清除尚未结束的封禁。持久化使用墙钟、进程内等待使用单调时钟，处理系统时钟变化及状态文件损坏；状态不明时保守暂停并报出原因。

### 3.4 冷却后分阶段恢复，不立即回到原始速度

建议初始参数，实施和自然轮次观测后再定标：

- 封禁到期后只放行 **1 个**已有任务本来需要的轻量请求，不另开测试扫描、不循环探测。成功前其他线程不放行。
- 恢复起步间隔 `max(事件前间隔×2, 1秒, 配额要求的间隔)`。正常事件同批只计算一次；若事件前已是 2 秒，应从至少 4 秒起步，不能因新封禁反而提速。
- 每经过 **120 秒且至少 60 次健康响应**，间隔至多缩短 **20%**；两个条件均满足才提速。429/418 立即退出恢复；持续网络超时或 5xx 时保持/收紧并退避，不把它们视为健康。
- 恢复上限由经核验的权重窗口、供应商用量头和本地保守余量共同决定。建议最多使用官方已确认额度的 **70%**，其余给其他流量和测量误差留余量；这不是共享 IP 不会超额的保证。
- 禁止在每次失败时无限乘二并无期限占用任务。若当前可用速率已不足以在小时预算完成，进入“受限、分段续接”并报告；不得通过上限截断把间隔变短、违背冷却。
- 重启后保留降速阶段，至少完成一次健康观察窗才允许提速；不能把重启或切换 IP 当成恢复机制。

健康请求数从所有相关入口统一累计；重试、取消、缓存命中不算成功 HTTP。用量头缺失时，只能在审阅过的保守本地预算内运行，不能推断“用量为零”。

## 4. 第二部分：让等待、请求和任务使用同一个截止时间

### 4.1 贯通任务时间预算

`request_gate` 暴露只读的剩余时间、剩余请求数和取消状态；调用方传入绝对截止时间，禁止各层重新起一个 30 分钟计时器。

处理顺序：检查任务 → 计算权重与剩余预算 → 可取消的节流等待 → 再检查任务并原子预留请求额度 → 发送 → 有界读取/解码 → 保存结果。

- `pacer.wait()` 接收绝对截止时间和取消检查；分段等待建议不超过 1 秒，便于暂停和及时让出。
- 冷却下一可用时刻已经超过截止时间，立即返回结构化阻塞原因；不睡完整冷却后再报任务超时。
- 建连/读取 timeout 使用 `min(原15秒, 剩余可用时间)`；检查响应体循环读取和解析边界。socket 的 inactivity timeout 不等于整个请求的墙钟时限。
- task 的 6,000 次预算按真实 HTTP 尝试统一扣减；重试也扣。同一请求不得被不同层重复扣费，等待未发出不得算 HTTP。
- 超时后停止新增逐币工作；已在途请求有界收尾，保存已完成证据，释放数据 worker。逐币循环、归档、业务回放均需有取消点和独立可续接段。
- 请求截止时间比任务硬截止至少早 30 秒，为收尾留空间。若底层实现无法中断阻塞线程，必须限制连接/读取并实测收尾上界；不能在旧 HTTP 仍运行时释放通道并启动下一个任务。

### 4.2 小时预算建议

以下是**待实施参数**，并非声称现网已经修改，也不保证第一次降速恢复中的全量轮次一定完成。

| 参数 | 当前 | 建议 |
|---|---|---|
| 两任务触发 | 每小时 +120 秒 | 保持 |
| 数据通道 | 单 worker | 保持 |
| 单任务全局上限 | 1,800 秒 | 保留为上限；实际受下面小时配额进一步约束 |
| 同一目标小时总预算 | 两任务分别计时，合计可超过一小时 | 从计划触发时刻起最多 3,000 秒（50 分钟），排队不重置 |
| 市场任务初始份额 | 最多30分钟 | 1,500 秒（25分钟，含收尾） |
| B1H 初始份额 | 最多30分钟 | 1,200 秒（20分钟，含收尾） |
| 本小时剩余300秒 | 无明确统一分配 | 可分给未完成主任务；只能用真实剩余时间，禁止侵占下一轮 |
| 下一周期安全间隔 | 无明确保留 | 本周期50分钟预算后至下轮约10分钟；补齐切片仍须可让出 |
| HTTP 次数上限 | 每任务6,000次 | 暂不提高，新增权重窗口限制 |
| 发布质量门槛 | 关键字段覆盖90% | 保持，并保留原字段有效性/新鲜度检查 |

份额是控制占用的初值，不是降低质量要求。实施前先用历史遥测回放估算；若正常供应商速度下仍不足，应先完成第6节增量采集，不能通过缩小份额就宣布修复完成。

若市场约2,400次、B约2,300次，合计约4,700次，仅在45分钟内派发就需平均约1.74次/秒；50分钟约1.57次/秒，均未计计算、冷却及不同权重限制。这是容量下界示例，B实际增量请求量会变化。不能仅把间隔恢复到1秒就保证每小时完成。

估时使用实际剩余 endpoint/参数、可用权重、近期网络耗时及本地处理耗时，不能只用“剩余合约数×固定秒数”。冷却时可用吞吐为零。输出预计完成时间和不能完成的原因，估计不能替代硬截止。

## 5. 第三部分：排队、断点与结果一致性

### 5.1 队列不反复从第一个币重新开始

- 保持原 task ID、reason、target_close_boundary 和历史记录；增加 checkpoint、执行段、剩余需求与供应商状态，不伪造新一轮成功。
- 每个币/来源的成功结果先保存，已完成部分不因任务时间片结束全部丢弃。下一段优先未完成部分；轮转起点，避免尾部合约长期得不到采集。
- 一小时内优先两项主任务，后台补齐只在无到期主任务时使用原有短切片，并受同一限速器约束。
- 下一小时的新鲜市场采集与旧历史回放分别排队；合并重复的采集需求时，保留每个目标小时的需求账本。B确认涉及的历史根按时间顺序恢复，不能跳过旧根直接写完成水位。
- 长冷却期间任务保留“等供应商恢复”的需求但不持有 worker，不反复创建相同任务；冷却到期也只有一个受控入口获取试探名额。

### 5.2 哪些数据可以续用，哪些不能拼接

| 数据 | 续用规则 |
|---|---|
| 已收盘1H/4H/日线 | 以市场、symbol、周期、open_time、版本/hash校验覆盖及连续性，保留修订重叠窗 |
| 历史OI/LSR | 只有接口语义、目标周期、anchor、最大滞后都符合既有契约才复用 |
| 当前OI、24H ticker等即时字段 | 保留取得时间，遵守原有新鲜度/一致性检查；过期必须重取，不能跨几个小时拼成一份“当前快照” |
| 未收盘K线 | 不作为已收盘信号依据；不得借增量优化改变策略边界 |
| 配置/权限/供应商402等阻塞 | 保留原因及需求，不把清除需求当补齐成功 |

只有关键字段满足既有门槛及时间语义，才原子替换 `scan.json`。采集成功、原始归档成功、历史业务逐根重算、策略结果更新分别验收。缺数据不能写为0；归档待生效不能当策略已恢复。

## 6. 第四部分：减少每小时重复全量拉取

市场扫描当前对每份合约每小时取最多1,500根4H、1,000根日线，既增加权重，也拉长恢复期。B已有增量/修订逻辑，不能粗暴改成只取最后一根。

建议第二阶段增加可复用的历史缓存：

1. 初次建库/确认缺口时才拉足指标所需历史；完整缓存按目标闭合边界计算缺口。
2. 4H/日线未到新收盘边界时，复用经检查的历史；到新边界只补缺口和必要重叠修订窗。修订窗长度在对照实验后冻结，不能本方案未经验证就直接改成1根。
3. 主站与B可共享原始已收盘证据，但各自按策略契约计算，不共享未经核验的最终信号值。
4. 合约更名、交易场所差异、新上市、停牌/退市、断档、缓存损坏有显式分支；不能只用币名当身份键。
5. 先做不发网络请求的历史回放：同一批原始证据下，对比全量与增量的K线/hash、指标数值、事件时间及结果。通过后再进入自然小时轮次观察。

不改 EMA/B/C 策略阈值，不改变 OI/市值单位，不启用自动清理，不删除旧1H数据；不让前端打开页面触发行情采集。

## 7. 状态与日志：能区分慢在哪里

后端增加以下可审计字段，现有状态接口兼容追加；先不改主站颜色、布局或导航。

- 当前任务/目标收盘边界、最后合格快照时间、当前轮状态分别记录。
- `pacer_interval_ms`、限流事件ID、封禁/冷却截止时间、恢复阶段、下一次允许派发时刻。
- 请求权重预算/已用量/来源、响应中的限额用量头、HTTP状态、Retry-After、必要且脱敏截断的错误code/message；不记录密钥、完整鉴权URL或出口IP。
- 分离队列等待、节流等待、供应商冷却、HTTP耗时、数据库/本地计算、收尾耗时；避免“30分钟任务”只有一个总耗时。

## 9. 验收方法

### 9.1 离线测试：不得为了复现而真的触发币安封禁

1. 假时钟+并发响应：8个在途请求中3条418，只产生一次降速；Retry-After取最晚；冷却后新试探失败产生新事件。
2. 冷却严格性：到期前零新派发；重启仍不能派发；Retry-After日期/缺失/异常及墙钟变化有覆盖；冷却解除不爆发补发。
3. 恢复过程：未满120秒或不足60健康请求不得提速；每次最多20%；权重预算高时不得提速；再次429/418立即退出；成功不自动清空封禁。
4. 时限贯通：冷却超过剩余时间立即让出；慢响应体、重试、本地循环、取消和在途收尾均有界；旧请求未结束前不运行下个数据任务。
5. 预算与排队：两个任务串行、总时限不超过50分钟；排队不重置截止时间；没有尾部合约饥饿；B历史根不被跳过；已存证据可续接且不重复计数。
6. 数据一致性：同一证据输入下全量/增量指标与事件一致；覆盖不足保留旧快照；过期即时字段不拼接；原始修订、gap、连续水位及待生效需求保留。
7. 页面隔离：打开主站/持续追踪/历史页面只读已保存数据，不产生额外行情HTTP；原页面布局与颜色保持。

### 9.2 自然小时轮次：至少连续3轮并覆盖一次4H收盘

- 不额外发起扫描，不并跑人为探测；等待项目自身计划触发，绑定真实task ID及目标边界。
- 调度正常、市场合格快照按小时发布、B本轮所需合约完成评估；合法缺证据需分来源说明，不能统称成功。两个任务在共同预算内完成且没有持续积压。
- 全时段真实遥测统计429/418、超时、权重、降速恢复与耗时分解；“未观测到限流”只代表观测时段，不保证以后永不触发。
- 任务结束后至少再观察一个补齐切片；分开核对归档与业务重算，列出仍有的权限/配置/402等遗留。它们不要求在本降速修复中凭空解决，也不允许因此假报全链路正常。
- 以发布前建立的同范围key/hash清单验证新增、修订及旧证据保留；若没有全量基线，验收报告明确覆盖范围，不作全量无损承诺。

若自然轮次仍超过预算，先按耗时分解和权重定位，调整请求复用/预算分配；不能擅自增加线程、绕开封禁、降低90%门槛或改策略阈值。
