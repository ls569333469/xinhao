## 4. 必须修复的问题

### 4.1 P1：事件账本全量读写与重复背景

`b_accumulation_store.py`的`cursor/list_events/ensure_observation_start/commit_symbol`会多次读取全市场JSON，提交又整体写回。`b_evidence.py`背景含最多1499根4H原始输入，`b_observe_evaluate.py`每条事件保存两份背景和168根1H基准，修订继续保存旧快照。

因此后续虽然只下载一根，仍可能读写百MB账本。不能只把本轮慢归因于首次预热，也不能通过删除背景字段/历史来解决。

### 4.2 P2：缓存双次全历史读取

`b_observe_runner.py:42/60`前后两次加载该合约所有1H缓存。第一次仅为决定续采起点；第二次计算又从头解压校验。随着历史增长，这类处理成本继续上升。

### 4.3 P1：OI与LSR共用最大水位

`b_public_adapter.py:46/47`对两路样本取最大时间戳再续采。已离线复现：OI停在T−10h、LSR到T，下一轮从T−1h开始，OI中间遗漏区间得不到恢复。需分来源水位和内部缺口，不能只把max换成min了事。

### 4.4 P1：新边界需求未形成可靠消费链

`task_service.py:_enqueue_b_observe`会复用任意在途B任务；自动调度随后推进next_due，未把新目标写成持久待补范围。手动统一入口已保存新请求目标并显示pending_range，但显示不等于已经自动补跑。

这证明存在时效与恢复链缺口，尚不能据此断言所有小时永久漏评：下一新目标的runner可能补回来。要求是让需求持久、可查、可消费，不依赖用户再次点击碰巧恢复。

### 4.5 P1：Windows归档原子替换冲突

本轮两份4H观测取得后未进入发布结果，错误为临时文件替换observations.jsonl时WinError 5。扫描完成数与成功落盘数必须分开，不能在文件提交失败后标记成功。

## 5. K线缓存：首次一次、后续补差值

### 5.1 首次与正常增量

- 首次合约无缓存：按现行预热规模取得约500根1H，连续性、闭合边界、单位及hash验证后落库。
- 已有连续数据至T，目标T+1h：只请求新增缺口，允许回叠最近2根检查供应商修订；同值复用，只新增1根。
- 数据至T，目标T+48h：分页取得48根及必要重叠；重叠不计为新增，不重做500根预热。
- 尾部已到目标但中间缺1根：补内部缺口，不能以最大时间戳冒充连续覆盖。
- 新上市合约不足168根：保存真实数据并标warmup_short，不补零、不循环请求上市前空数据。
- 同目标重复扫描：保留必要的修订复核和本次取得证据，不重复新增K线、事件或通知。

### 5.2 轻量元数据与有限窗口

在现有缓存索引上增加/完善合约周期的轻量覆盖元数据与缺口索引。查询最后两根、最早待补区间、连续归档水位时不解压历史载荷。

计算按计划读取所需范围：新事件的前168根、真实h/h+1、未确认事件、待补证据事件与修订依赖区间。最近约170根只能是普通增量工作的最小局部窗口，不得作为所有任务统一上限。

补48小时可能需要其前168根基准及边界保护根；早期源修订可能影响后续168根事件量比及确认、结构价格引用，按依赖图定位重放范围。存储历史不删，读取窗口可按需收窄。

无完整背景或连续基准时技术判断保持unknown并登记重评需求；已确认缺口被补齐后再推进连续水位。

## 6. 水位与缺口模型

“水位”表示有证据支持的处理进度，不是任务开始时间或最大返回时间戳。建议持久化如下概念，具体表名可按现有架构实现。

| 状态 | 粒度 | 含义及推进条件 |
|---|---|---|
| requested_through | 策略/市场范围，按请求及配置版本关联 | 用户或已开启计划要求的固定最高目标，先持久化再回复受理 |
| fetched_through | 合约/周期/来源 | 仅表示取得结果，不代表已归档或已判定；失败样本也保留原因 |
| archived_contiguous_through | 合约/周期 | 已验证并持久化且连续可读取的K线覆盖；最大尾部另存 |
| OI source cursor | 合约或可信pair/period/profile | OI独立最新有效样本、连续覆盖、内部缺口、重试信息 |
| LSR source cursor | 合约或可信pair/period/profile | LSR独立状态，成功不替OI推进 |
| processed_through | 合约/策略/规则版本 | 每小时观察判定已提交，可含unknown但原因及重评队列必须存在 |
| unresolved/replay ranges | 合约/来源或规则依赖 | 内部缺口、未知背景/结构、源修订需要重放的准确范围 |

unknown结果可以形成已记录的观察，不等于资格有效。区分“已记录unknown”和“完整可判定”，展示各自分母。

**任务success ≠ 该小时已全覆盖。** 对固定目标、明确合约分母与规则版本，同时核对`archived_contiguous_through`、`processed_through`、`unresolved/replay ranges`以及OI/LSR各自水位和缺口。K线连续归档、观察记录完成、资格可判定分别验收；`processed_through`允许unknown时，不能据此宣称资格证据齐全。存在未解决范围或历史不可恢复时，列明受影响小时/合约及原因，不能用最大尾部时间、task.success或账面588/588替代覆盖证据。

缺口记录至少含：来源、market/symbol或pair、interval/period/profile、左闭右开时间范围、原因、首次发现、最近尝试、下次可重试、尝试次数、状态及不可恢复原因。只有相关归档与判定提交成功才能关闭对应缺口。

## 7. 固定目标与补采调度

### 7.1 在途复用不改变旧目标

1. 每次手动或计划请求先固定本次target_close_boundary及配置版本。
2. 相同幂等键返回原请求身份和原目标；同目标在途工作复用。
3. 新目标到来而旧任务未结束：旧任务目标不改，新目标需求持久化，返回实际任务目标与待补范围。
4. 后续消费者处理持久需求，不以“已返回旧任务ID”代替已安排新边界。

### 7.2 合并区间、逐小时评估

不要求每漏1小时就创建一份完整全市场任务。连续待补边界可合并为一个区间；按合约缺口补数据，再按时间升序评估其中每个小时，h+1仍按真实相邻根绑定。

每个策略/范围保留有限的在途/待执行补采工作，使用事务认领/租约与唯一键避免多消费者重复启动。若期间有更高目标，持久更新需求上限；正在运行的切片仍使用原固定上限，下一切片再消费新增部分。

只有已开启计划持续产生未来边界。手动一次点击只消费该次及后续明确请求的目标，不在计划关闭时无限追赶当前时间。明确展示“本次目标已完成”与“距当前最新闭合边界仍落后”，不把时钟流逝自动授权为新扫描。

4H同样按自己的4小时闭合边界登记与去重。完整策略扫描所需实时字段仍保留真实采样时刻；已有同目标K线/背景证据可复用，但不能用旧OI/价格伪装新采样。

### 7.3 长离线与预算

按最早未补区间分页，设置请求/时长预算和共享退避。预算用尽保存next_page_start、已归档范围及剩余缺口，不标全覆盖、不自动重建完整历史。

重启后恢复待补需求和已提交水位。已被中断任务保持明确中断身份，另建有恢复关联的后续工作，不把失败旧任务静默改成成功。手动/自动权限与恢复范围单独判断，计划关闭不自动启用未来计划。

## 8. OI与LSR分别续接

- OI、LSR各自计算请求起点、重叠窗口、历史可得范围与内部缺口；各自记录成功或错误。
- 一个接口失败，另一个成功结果照常持久化，不能相互覆盖进度。请求预算不足时优先保存可取得证据及剩余工作。
- 保留source_timestamp、first_retrieved_at、revision_retrieved_at、来源、period、profile、单位和载荷hash；补采时间不能冒充当时实时取得时间。
- “接口返回空”区分暂未发布、已知无该统计、超历史期限及接口错误；不能一律当作覆盖完整。
- 超出供应商历史可回溯期限的缺口标不可恢复；保留技术事件，结构资格unknown。不能用今天市值、现在OI、当前LSR回填历史。
- COIN-M使用可信pair及contractType适配，OI数量、标的名义值与USD换算分开；需要价格换算时价格绑定同源样本时点。
- 补证据后以依赖区间重评相关事件；若结论/输入变化追加修订，同输入不追加修订，不重复通知。

## 9. 事件持久化与背景证据复用

### 9.1 按键增量事件库

建议在`runtime`增加版本化B事件SQLite存储，通过现有BAccumulationStore接口适配，避免调用方分别实现新旧逻辑。

建议逻辑实体：events、event_revisions、symbol_cursors、symbol_rounds、outbox、migration_state、evidence_refs及replay_jobs。事件按稳定event_id查询，合约事件按market/symbol索引；列出轻量摘要时不加载所有背景原文。

单合约事务提交：事件变更、修订身份、处理cursor、轮次摘要、outbox和证据引用/generation。已有输入指纹相同则复用，不追加同内容修订。通知唯一键至少含event_id及通知类型，保留first_seen/confirmed_first_seen等历史身份。

缓存数据库可先单独提交不可变数据；事件事务失败时缓存保留、判定cursor不推进，重试利用缓存重放。禁止假装两个独立SQLite事务天然跨库原子；以幂等写入和可恢复状态机处理崩溃缝隙。

SQLite并发采用短事务、明确busy_timeout及可见错误；WAL如采用须把WAL/SHM、checkpoint和在线备份纳入恢复流程。共享清理/引用保护锁只包必要临界区，不在全局锁内做大JSON序列化或网络请求。

### 9.2 不可变证据引用

将两份4H背景输入、1H基准窗口及其他重载证据按内容寻址存放，事件只保存准确引用与主要判断值。
