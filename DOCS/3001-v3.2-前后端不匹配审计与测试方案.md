## 1. 摘要



### 1.1 匹配度总览



| 维度 | 判断 | 一句话 |

|---|---|---|

| 核心读写链路 | **大体打通** | `runtime/b-accumulation-events.json` → `GET /api/b-observe/events` → `b-observe.html` / 统一台 `bEvents` 可读 |

| 设置契约 | **部分对齐** | 任务页可改 `observe`/`timing`；设置绑定页只保存 `scan`，且不展示下次观察时间 |

| 阶段文案 | **明显分裂** | B观察页用中文 `stage`；统一台用英文 `bstatus` 再映射另一套中文 |

| 手动跑一轮 | **后端有、前端无** | `POST /api/b-observe/run` 已实现，页面无入口 |

| 在途复用 | **语义落空** | `in_flight_reuse_key` 写入 `request_hash`，入队却按「任意在途 B 任务」复用，不按边界比对 |

| 同期门禁 | **底层与展示层语义不同** | `contemporaneous_ok` 可返回 fail；`structure_at` 把非 pass 一律收成 unknown |

| 确认优先 | **方案写了、实现弱校验** | 第13章要求先确认再评新事件；流水线按「每根当 h 连同 h+1」算；相关测试几乎不验顺序 |

| A/B 隔离 | **文件隔离、展示汇合** | B 不写进 A 池文件；统一台只读合并 `bEvents` 到展示行 |



总体：**P0–P4 骨架已在仓库落地，前后端「能看见」；契约与交互层仍有多处可导致误判/误操作的断层。** 不宜当作「已验收闭环」。



### 1.2 高优先级 Top 7（初版；深度增补见 1.3）



1. **在途 B 任务复用不按目标收盘边界匹配**（高 / 交互·链路）

3. **`POST /api/b-observe/run` 无前端入口**（高 / 接口·交互）  

4. **设置绑定页保存扫描时不带 `observe`/`timing`，且无「下次观察」展示**（中高 / 设置）  

5. **同期滞后在证据层被改成 unknown，与方案 B07「不通过」表述易混淆**（中高 / 字段·文档漂移）  

6. **任务来源文案未覆盖 `manual_b_observe` / `scheduled_b_observe`**（中 / 交互）  

7. **`test_confirm_before_new_h` 名实不符，确认优先顺序几乎未测**（中 / 文档漂移·测试缺口）

## 3. 问题清单（按严重度）



### 高



#### H1 / 高 / 交互·链路

- **现象**：只要已有任意排队/运行中的 `b_observe_1h`，再次入队（含不同目标收盘边界）会直接复用旧任务，不会按边界区分。  

- **证据**：`task_service.py` `_enqueue_b_observe`：计算了 `in_flight_reuse_key(target_close_boundary)` 写入 `request_hash`，但查询条件仅为 `kind='b_observe_1h' AND status IN ('queued','running')`，未比对 `request_hash`/边界。`test_v32_execution.py` `test_S01_S02_inflight_target_and_browser_settings` 用 `T` 与 `T+H` 入队，断言 `a==b` 且 `request.target_close_boundary==T`（把「串边界复用」固化成了期望）。  

- **影响**：手动补跑下一小时、或跨边界触发时，可能白跑错目标；调度与手动互相踩脚。  

- **建议验证/修复方向**：入队复用应按 `request_hash`（或 `target_close_boundary`）相等才 reuse；不同边界应排队或拒绝并返回明确错误。同步改 S01 测试期望。



#### H2 / 高 / 字段·交互

- **现象**：同一事件在 B观察页与统一工作台用两套阶段语言，用户对照时会对不上。  

- **证据**：  

  - `b_observe_api.present()`：`待确认` / `完整确认` / `结构不满足` / `资格待核验` / `确认未通过` / `确认待核验` / `已更正` / `旧版待复核`  

  - `b-observe.html` 筛选项与上述中文一致  

  - `unified-core.js` `bstatus`：`pending` / `complete` / `fail` / `confirmation_failed` / `corrected` / `legacy` / `unknown`…  

  - `unified-workbench.js` `bLabel`：`完整资格确认`、`待下一小时确认`、`资格不满足` 等（与 B页「完整确认」「待确认」字面不同）  

- **影响**：雪球在两个页面核同一条记录时，阶段名不一致，易误判「是不是同一种完成态」。  

- **建议**：统一「展示字典」：要么 API 只吐机器码、两端共用同一映射表；要么统一台也读 `stage` 字段。



#### H3 / 高 / 接口·交互

- **现象**：后端有手动触发观察轮次的接口，前端没有任何按钮/调用。  

- **证据**：`server.py` `POST /api/b-observe/run`（未启用时 409「B观察未启用」）；全站 html/js 检索无 `/api/b-observe/run` 调用（仅 `server.py` 自身）。`b-observe.html` 只有刷新/CSV/报告/清理设置。  

- **影响**：开启观察后只能等调度；排障或补跑依赖手搓 API，普通页面操作闭环断裂。  

- **建议**：在任务页或 B观察页增加「跑一轮」（受 `observe.enabled` 与 Origin 写校验约束）；或在文档明确「本版故意不提供 UI」。



#### H4 / 高 / 字段·文档漂移

- **现象**：方案/单测对「同期门禁失败」表述为 fail；真正进入结构资格时，滞后样本被改成 unknown，不会单独打成经济意义 fail。  

- **证据**：  

  - `b_contemporaneous.contemporaneous_ok`：`delta>max_lag` → `fail`；`s>t` → `fail`  

  - `b_evidence.structure_at`：`oq='pass' if oq=='pass' else 'unknown'`（注释写明 stale/future 不作经济 fail）  

  - `test_v32_codex_gates.test_gate_edges` 期望 contemporaneous 层 fail；`test_v32_execution.test_B07_B08` 期望 `structure_at` 在 lag=300001 时 `oi_quality=='unknown'`  

  - 方案 v3.2 第3章/验收表 B07 写「后两个不通过同期门禁」  

- **影响**：页面上更常见「资格待核验/unknown」，而不是「同期失败」；和方案字面、和底层函数返回值不一致，联调时容易吵。  

- **建议**：在方案与 UI 明确「门禁层 fail → 资格层 unknown（证据不足）」的两级语义；或让 `structure_h.reasons` 在详情里固定展示「超出5分钟门禁」。



#### H5 / 高 / 链路·交互

- **现象**：任务页能开关 B观察并保存；设置绑定页（`config-runtime`）保存扫描时只提交 `version+scan`，不提交 `observe`/`timing`，也没有观察开关控件。  

- **证据**：`tasks-runtime.js` `saveSettings` 组装 `timing`/`observe`；`config-runtime.js` `saveScan` 仅 `body={version,scan}`；`renderScan` 用 `state.scan.observe`（此处 `state.scan` 实为整份 `/api/settings` 响应，能读到顶层 `observe`，但无法从该页改）。两端都不读 `observe_next_due`。  

- **影响**：两套设置入口行为不一致；开启观察后看不到「下次观察几点跑」。  

- **建议**：设置绑定页只读展示 observe/timing/下次时间，并禁用会让人以为能改的控件；或与任务页共用同一保存载荷。

### 中



#### M1 / 中 / 交互

- **现象**：任务列表来源文案映射只有 `manual/scheduled/recovery`，B 观察实际写入 `manual_b_observe` / `scheduled_b_observe`，界面会显示英文原串。  

- **证据**：`tasks-runtime.js` 渲染 `{manual:'手动',scheduled:'定时',recovery:'重启补扫'}[t.reason]||t.reason`；`server.py`/`task_service.py` 入队 reason 为 `manual_b_observe` / `scheduled_b_observe`。  

- **影响**：可读性差，排障时不像「定时观察」。  

- **建议**：补映射表。



#### M2 / 中 / 链路·文档漂移

- **现象**：方案第13.2节要求对每根 bar「先处理 expected_confirmation_open_time==b 的确认，再评新 h」；实现是对每根 bar 当作 h，在 `calculate_event` 内联评 h 与 h+1。  

- **证据**：方案 `## 13.2`；`b_process_order.process_bars_in_order` 循环内 `evaluate_h_event` + `calculate_event`，无「确认优先」分支；`test_v32_codex_gates.test_confirm_before_new_h` 只断言 `new_events>=1`。  

- **影响**：多数独立事件终态可能接近，但同根既是确认又是新事件、或确认改写与新事件争用 cursor/outbox 时，顺序风险未被锁死。  

- **建议**：补边界样本测试（确认先于新信号），再决定是否改流水线顺序。



#### M3 / 中 / 字段

- **现象**：CSV 不含 `coverage`，也不含统一台关心的 `bstatus`；JSON 有 `stage`/`coverage`，CSV 列固定 `CSV_COLS`。  

- **证据**：`b_observe_api.py` `present` 写 `coverage`；`CSV_COLS` 无 `coverage`。  

- **影响**：导出表与页面详情字段不完全同构，方案「表/详情/CSV同源」打了折扣。  

- **建议**：CSV 增加 `stage`（已有）外的 `coverage`，或文档写明 CSV 子集。



#### M4 / 中 / 设置

- **现象**：`closeOffsetSec` 后端要求 Python `int`；前端 `Number(input.value)`，用户若填小数，JSON 可能变成 float，PUT 被拒。  

- **证据**：`observe_config.validate_timing`：`type(...) is not int`；`tasks-runtime.js`：`closeOffsetSec:Number(...)`。  

- **影响**：偶发保存失败，错误信息对用户不友好。  

- **建议**：前端 `Math.trunc`/`parseInt`；或后端接受整值 float。



#### M5 / 中 / 接口

- **现象**：写接口强制 Origin 同源 + `Sec-Fetch-Site`；B观察页清理设置 PUT `/api/cache/retention` 从该页发起可通过，但用外部工具/跨端口会 403。  

- **证据**：`server.py` `write_api` Origin 校验。  

- **影响**：排障脚本易误判「接口坏了」。属安全设计，但文档应写清。  

- **建议**：在落地说明写「仅本机同源页可写」。



#### M6 / 中 / 字段

- **现象**：`observe.oi_lsr_max_lag_ms` 在配置里固定存在，但 runner → `structure_at` / `pick_sample_at_or_before` 未传入该配置，始终用函数默认 300000。  

- **证据**：`observe_config.OBSERVE_DEFAULT`；`b_observe_runner` 调 `structure_at` 无 `max_lag_ms`；`b_evidence.structure_at` → `pick_sample_at_or_before` 默认 300000。因 `validate_observe` 锁死等于默认，目前行为碰巧一致。  

- **影响**：配置项形同虚设；将来若放开修改会静默不生效。  

- **建议**：显式接线，或文档标注「仅占位、以代码默认值为准」。



#### M7 / 中 / 文档漂移

- **现象**：本机已有 `runtime/b-accumulation-events.json` 仍为 `b-accumulation-events-v1`，加载时会被标 `migration_status=legacy_unverified`，阶段变「旧版待复核」。  

- **证据**：仓库 runtime 文件 schema；`b_accumulation_store._load` 对 `schema_version<2` 打 legacy。  

- **影响**：页面上大量「旧版待复核」并不等于本轮规则刚算出的结果；易被当成当前观察失败。  

- **建议**：P5/验收时区分 legacy 与新写入；需要时按 r2 重核，而不是口头说 A 档完成。



#### M8 / 中 / 交互

- **现象**：观察关闭时若仍有任务跑完，`status` 被标成 `cancelled`（由 `skipped` 映射），进度文案「B观察关闭已跳过」。  

- **证据**：`task_service._run`：`if status=='skipped': status='cancelled'`。  

- **影响**：与用户主动点「取消排队」的 `cancelled` 混名。  

- **建议**：独立状态或 result.skipped 徽章。



#### M9 / 中 / 链路

- **现象**：统一台通过 `/api/unified/signals` 把 B 事件挂到扫描行的 `bEvents`；合约若不在 `scan.json` 会生成「B archive only」行。  

- **证据**：`unified_workbench.load_payload`。  

- **影响**：不是写串 A 池文件，但市场页会出现「只有 B、没有 A 行情」的行，需在 UI 标明来源。  

- **建议**：列表角标「仅 B 归档」。



#### M10 / 中 / 测试缺口

- **现象**：P4 测试只覆盖 list/csv 符号与 pool 名；无前端契约、无 run 接口、无 settings 往返、无 stage 枚举对齐测试。  

- **证据**：`test_v32_p4_b_api.py` 仅 `test_list_and_csv`。  

- **影响**：回归挡不住本文所列断层。  

- **建议**：见第5章测试方案。

### 9.1 深度新增问题

#### H6 / 高 / 字段·交互 · 深度增补
- **现象**：同一事件在 B观察页与统一台可能落到**不同语义类**，不仅是文案用词不同（H2），而是判定树分叉。
- **证据**：
  - `b_observe_api.present`：`technical_event != 'pass'` → 一律「已更正」（含 unknown/缺省）
  - `unified-core.js` `bstatus`：仅 `technical_event==='fail'` → `corrected`；其它非 pass → `unknown`；且 `structure_gate==='fail'` 优先于 te 非 pass
  - 离线对照：`te=unknown` → stage=已更正 / bstatus=unknown / bLabel=技术确认 / 资格待核验
- **影响**：用户两边对同一 event_id 会一个当成「已更正」、一个当成「待核验」。
- **建议验证**：fixture 写入 technical_event=unknown 与缺省 te，对照两页与 CSV stage。

#### H7 / 高 / 文档漂移 · 深度增补
- **现象**：方案 §13.4 规定的 B 视图阶段分类与现行 UI/API stage 枚举不是同一套词表。
- **证据**：
  - 方案：疑似吸筹 / 待确认 / 技术确认 / 完整确认 / 历史记录
  - b-observe.html：待确认 / 完整确认 / 结构不满足 / 资格待核验 / 确认未通过 / 确认待核验 / 已更正 / 旧版待复核
  - 统一台 bLabel：完整资格确认 / 待下一小时确认 / …（第三套）
- **影响**：按方案验收「页面阶段」会对不上号。
- **建议**：以实装枚举回写方案，或做映射表三列（方案名 / stage / bstatus）。
