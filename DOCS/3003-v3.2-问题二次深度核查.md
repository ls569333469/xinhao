## 1. 深挖卡 H1 — 在途复用不按边界

### 1.1 复现路径（静态可推）

1. 已有 `queued/running` 的 `b_observe_1h`，其 `request.target_close_boundary=T`，`request_hash=b_observe_1h:T`。  
2. 再次调用 `_enqueue_b_observe(..., T+H)`（手动 run 跨边界，或调度与手动重叠）。  
3. 查询：`WHERE kind='b_observe_1h' AND status IN ('queued','running')` —— **不比对** `request_hash` / 边界。  
4. 返回旧 `task_id`，`reused=True`。

离线最小步骤：`test_S01_S02_inflight_target_and_browser_settings` 已用 `T` 与 `T+H` 入队并 `assert a==b`。

### 1.2 根因定位

- 函数：`task_service.TaskService._enqueue_b_observe`（约 L488–503）。  
- `reuse = in_flight_reuse_key(target_close_boundary)` → `b_observe_1h:{boundary}`（`b_observe_schedule.in_flight_reuse_key`）。  
- **写入** INSERT 的 `request_hash` 列；**查询**却忽略该列。  
- 分支条件：`if active: return active['id'], True` —— 任意在途即复用。

### 1.3 影响面

- API：`POST /api/b-observe/run`（返回 `reused` + 调用方传入的当前 `boundary`，可能与任务内实际边界不一致）。  
- 调度：`_tick_b_observe` → `_enqueue_b_observe(..., scheduled_b_observe, boundary)`。  
- 任务表 / 进度文案；跨小时补跑白跑错目标。

### 1.4 同族 / 连带

- **M22**：同文件 `candle_range` 入队用 `request_hash=? AND status IN (...)`；另有 UNIQUE INDEX `one_active_range`。`ai_research_batch_retry` 亦按 hash 查。唯 B 观察落空。  
- **M18**（已有）：前端无 run，故 `reused` 零处理。  
- S01 把错误期望固化（§16）。

### 1.5 证据强度

**代码必达** + **测试固化**（S01 PASS 即证明串边界）。

### 1.6 误判风险

用户以为「又提交了一轮下一小时」，实际挂在旧边界任务上；对账时看到 `reused:true` 与 `target_close_boundary` 响应字段不一致更易吵。

## 6. 深挖卡 H6 — `present().stage` vs `bstatus()` 判定分叉

### 6.1 判定树（精确分支）

**present**（`b_observe_api.present`）顺序：

1. `migration_status==legacy_unverified` → 旧版待复核  
2. `technical_event != 'pass'` → **已更正**（含 unknown / None / 空 / 任意非 pass）  
3. 再看 `technical_confirmation`：pending / fail / unknown  
4. 再看 `structure_gate`：pass→完整确认 / fail→结构不满足 / 其它→资格待核验  

**bstatus**（`unified-core.js`）顺序：

1. `migration_status==legacy_unverified` **或** `(schema_version||0)<2` → `legacy`  
2. `technical_event==='fail'` → `corrected`  
3. `structure_gate==='fail'` → `fail`  ← **在 te 非 pass 的 unknown 之前**  
4. `technical_event!=='pass'` → `unknown`  
5. 再看 tc：pending / fail / 非 pass→unknown  
6. `structure_gate==='pass'` → `complete` / 否则 unknown  

### 6.2 technical_event 各取值对照表

固定：`tc=pending`，`sg=unknown`，`schema_version=2`，无 migration。

| technical_event | present stage | bstatus | bLabel | 分歧 |
|---|---|---|---|---|
| `pass` | 待确认 | pending | 待下一小时确认 | 用词差（H2） |
| `fail` | 已更正 | corrected | 已更正 | 对齐 |
| `unknown` | **已更正** | **unknown** | 技术确认 / 资格待核验 | **FORK** |
| `None`/缺省 | **已更正** | **unknown** | 同上 | **FORK** |
| `''` / 其它 | **已更正** | **unknown** | 同上 | **FORK** |

### 6.3 优先序分叉（本轮新挖 → M19）

| 输入 | present | bstatus | 说明 |
|---|---|---|---|
| te=pass, tc=pending, sg=fail | **待确认** | **fail** | present 先 tc；bstatus 先 sg=fail |
| te=pass, tc=fail, sg=fail | 确认未通过 | fail | 两边都偏「失败」，类不同 |
| te=pass, tc=None, sg=pass | **完整确认** | **unknown** | present 把非 pending/fail/unknown 的 tc 当成通过路径；bstatus 要求 tc==='pass' |
| te=unknown, tc=*, sg=fail | 已更正 | **fail** | present 在 te 一刀切；bstatus 先 sg |
| schema_version 缺/&lt;2，te=pass,tc=pass,sg=pass | **完整确认**（无 migration 字段时） | **legacy** | bstatus 额外看 schema_version；present 只看 migration_status |

离线全矩阵（te∈{pass,fail,unknown,None} × tc×sg，schema=2）：**44 / 80** 组语义类不一致。

### 6.4 影响面

B API stage、CSV stage、统一台筛选 `bStage`、详情 bLabel；磁盘存量经 `_load` 后两端都进 legacy（暂时「一致地旧」），**新写入 schema_version=2 后分叉立即暴露**。

### 6.5 同族

H2、H7、M19、M13/M21。

### 6.6 证据强度

**代码必达** + 离线 Python 对照（临时脚本，未改业务）。

### 6.7 误判风险

一边「已更正」、一边「待核验」；或一边「待确认」、一边「资格不满足」——用户以为两套数据。
