# 多报告同时生成：并发补充 v1.2

日期：2026-10-14（Asia/Shanghai）。补充 [v1.0](../research-iteration-20261014T112945Z/给GROK-投研迭代需求-模板B新任务检索核验与经验积累.md) 与 [v1.1](6016-给GROK-投研方案复核补充-v1.1.md)，原文件不改。本文件是需求补充，不是当前程序已支持并发的验收结论。

## 1. 先区分两种情况

| 场景 | 要求 |
|---|---|
| 一次选择多个币并确认 | 一个批次，保存明确目标列表；内部可按币/小组调度，逐币产出状态与报告 |
| 连续独立确认多个投研，包括同一个币 | 各自独立任务和实际新模型调用，可有界并发或排队；不得按内容相同合并 |

两种场景可同时存在。例如先发 STRK，再发 BTC，再发包含 STRK/ETH 的批次，三次确认身份各自独立。第一次 STRK 的结果不能代替第三次中的 STRK。一次确认连点/重传仍按幂等规则去重。

## 2. 调度：允许并发，超过上限排队

- 不要求无限同时运行；设置任务/供应商实际模型请求的并发上限，检索与模型调用可分别限流。一个多币任务不能绕过全局限制，无论启动多少 worker，总在途请求都受控。
- 初期建议模型在途上限保守从 2 起试；实际值按供应商限额和机器能力配置。这是实施建议，不是用户已确定的数值；能力不足可先用 1，页面必须如实显示排队。
- 每个任务独立显示排队、扫描、检索、生成、核验、成功/部分成功/失败等阶段，不以“另一个任务运行中”误报本任务失败。
- 批次按小组公平调度，避免大批次长期占满全部槽位；遵守供应商限流/退避和预算边界。429 不触发无上限重试，也不连带取消其他任务。
- 本轮无需新建分布式调度平台，现有执行器可先限制并发；如先串行交付，记录为“多任务排队已支持，真正并行待验证”。

## 3. 必须隔离的上下文

每次确认保存自己的 submission/task 身份、对象、模板/编辑、关注点、检索策略、模型/配置版本及预算；取证后再绑定本轮快照/来源。任务执行不能反复读取页面当前选择或最新全局配置替换冻结值。

以下内容必须按任务或调用作用域保存，不能用一个共享可变变量承接所有任务：进度、错误、当前合约、提示词、证据集合、模型输出、usage、取消标记及文件路径。共享服务对象可以保留，但其中这些状态必须隔离。不得把 A 的检索结果当 B 的证据，或让 B 的结束进度覆盖 A。

如果扫描器通过固定 `scan.json` 发布“最新快照”，任务完成扫描后应绑定不可变版本/副本；不能等待稍后再读这个全局文件，读到另一任务的快照。允许共享经过时效验证的不可变基础数据，但各自记录来源身份，不共享 AI 结果来替代独立研究。

## 4. 落盘与恢复

- 报告、原始响应及证据目录用任务/报告唯一身份命名；同币两份报告不得互相覆盖。
- 数据库提交与报告发布有明确一致性边界；并发写索引/日志须事务或等效同步，正文完整校验后再发布，不让 UI 读到半份 JSON/Markdown。单任务失败不损坏其他已完成报告。
- 执行器用事务性认领或等效机制，防止同一排队任务被两个 worker 同时执行；重启恢复不盲目重发结果未知的供应商调用，沿用 v1.1 REV-04。
- 所有日志按任务/attempt 标识关联，允许时间交错；凭证不入日志。旧库迁移保留历史报告与原扫描去重规则。

## 5. 页面：多任务可见，不抢当前阅读位置

- 任务列表显示对象/模式、创建时间、独立进度及排队原因，允许查看某个任务自己的错误与结果。多币批次展开后逐币可见成功/失败。
- 一个任务先完成可先查看，不必等待全部任务；同币不同确认保留各自时间与报告身份，列表标题继续简洁。
- 用户主动提交且未切走时可以打开该任务结果；用户已经切换去阅读别的报告后，后台任务完成只提示，不强行抢详情。响应乱序不得把用户当前报告正文替换成旧任务结果。
- 某个任务失败/待核验不能把另一任务成功正文放入该任务详情；与查看历史的行为区分。
- 若已有取消功能，取消仅作用于目标任务；供应商请求已发出时，不承诺立即终止或退款。当前没有取消入口时，本轮不强制新增，仅保证失败/停止不会串任务。

## 6. 调用与费用归属

记录关系建议为“确认/批次 → 子任务或合约组 → attempt → 真实供应商请求”。每次实际请求只计入一次任务总量。

多币合并一次模型请求时，共享该次真实 usage；供应商没有逐币拆分则逐币用量标未知/共享批次用量，不能把整次 usage 复制到每个币再累计。若做估算分摊，单列估算依据，不能称真实逐币账单。

一个任务的失败/重试费用不能归到另一个任务；同批补失败币保留原确认和成功报告。用户重新独立研究同币才新建确认和实际新模型调用。

## 7. 增补验收（可先用离线桩，无需为并发测试额外付费）

| ID | 场景 | 通过条件 |
|---|---|---|
| CON-01 | A/B 两份不同币同时执行，B 先返回 | 提示词/证据/快照/进度/正文/费用分别正确，无串线 |
| CON-02 | 同币独立确认两次，并发重传其中一次 | 两个独立任务；重传仅复用所属确认；输出互不覆盖 |
| CON-03 | 超过并发上限，同时有单币与多币批次 | 全局在途数不超限，其余排队；批次内部调用也计入上限 |
| CON-04 | A 超时/429，B 正常完成 | A 按边界退避/失败，B 不受错误状态污染；结果未知不盲重发 |
| CON-05 | 两次扫描交错、全局快照被后任务更新 | 两任务分别绑定自己的不可变 revision，不取错最后写入快照 |
| CON-06 | 用户看 A 时 B 完成，随后 A 的旧请求晚返回 | 当前阅读位置不被后台抢走，不显示错误任务正文 |
| CON-07 | 多 worker 认领同任务、并发落盘、写入中失败/重启 | 不重复执行、不丢已完成报告、不发布半成品；不确定调用保留状态 |
| CON-08 | 一个多币批次部分失败，补失败币 | 成功项保留，整批部分成功；只补失败对象，usage 不重复累计 |
| CON-09 | 多币共享一次请求 usage | 批次只计一次；逐币标共享/未知，不伪造精确分摊 |

交付时写明实际最大在途数、执行器/供应商限制、离线与真实环境各验证到哪一步。模型/检索/页面支持并发需分别取证，不能以“能建多个 task”推导整个链路已能同时安全生成。
