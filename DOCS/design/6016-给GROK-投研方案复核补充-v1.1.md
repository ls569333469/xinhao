## 2. 应优先澄清的四项 P1

### REV-01：预览冻结用户意图，取证后冻结实际证据

**第一版位置：§3 第 2–3 项、§6、RES-05/06。** 扫描并投研时新快照尚不存在，检索内容也只能在执行后取得。如果将“所有输入预览时已冻结”机械实现，就会误用旧快照、因本轮扫描改变 revision 而拒绝自己，或无条件信任后来任意内容。

采用两个阶段：

1. **意图冻结**：确认时冻结 submission_id、完整市场/合约身份、范围语义、当前快照或扫描并投研模式、档位、用户编辑、模型/配置/模板版本、检索策略与已确定的执行预算。当前快照模式绑定具体 revision；扫描并投研绑定扫描设置版本，明确新 revision 待生成。
2. **执行证据冻结**：本轮扫描/检索完成后绑定新 scan_id/revision、每份证据及哈希、取得时间、覆盖/缺口，再形成实际模型输入版本。不能把预览里的旧行情当成执行证据。

排队期间用户修改设置，任务使用可合法执行的冻结版本；如果旧凭证/版本已不可用，则明确冲突/失败，不静默替换。补充取证若不改变已确认范围、策略和预算，无需每条网页都重新确认；改变这些边界则重新确认。

范围建议本轮默认冻结为明确合约列表；如已有“新扫描结果自动选币”模式，则另外冻结选择规则与最大数量，不能和固定名单混用。相同币池仅改变屏幕排序，不应无意义地使预览失效；实际提交范围或研究顺序确受影响时才重新预览。

**增补验收**：新扫描产生 revision B 后正常绑定 B；不得绑定预览时 A，也不得把预期的 A→B 当冲突。排队期间篡改名单/模板/模型必须被发现。

### REV-02：去重必须覆盖数据库、持久化和恢复

**第一版位置：§3.1、RES-01/02/03。** 仅删除 find_cached 或修改前端按钮不足够。

只读源码核对发现 `task_service.py:80–81` 仍有 ai_research/scan_and_research 按 request_hash 的活跃唯一索引；`:183` 起也按内容查询活跃任务。因此 GROK 修改新任务语义时应检查**现存数据库升级路径**，不能仅更新新建库 SQL，否则第二次独立确认可能仍被旧约束挡住。

- 持久化 submission_id 与意图摘要，建立事务性幂等约束；独立确认换 ID，重传保持 ID。
- 同 ID 同意图返回同任务；同 ID 不同意图拒绝。扫描产生的新 revision 不改变原确认 ID。
- 内容哈希继续用于追溯，不能靠往证据哈希掺随机数假装不同内容。
- 冻结的非敏感输入/证据引用和执行步骤须可恢复，不能仅靠进程内 side channel。凭证按现有安全存储取用，不明文入任务库。
- 现存任务保留原身份；升级不删除历史任务/报告、不破坏原扫描或区间补查的去重规则。先在项目外数据库副本验证升级/重启，再按实际实施权限处理运行环境。

**增补验收**：现存旧库升级后，相同内容两次独立确认都能入队；同键并发重传只一个任务；重启后冻结输入仍完整，不换币、不换模板、不额外触发新确认。

### REV-03：检索路线要选定，并兼容证据形成时序

**第一版位置：§5.1 允许供应商原生工具，但 §6 又强调模型前冻结输入。** 这两种路线的证据取得时序不同，不能用一套“所有来源必须在首次请求前就存在”强行验收。

建议本轮先选一条能在当前供应商/协议实际跑通的路线，不必同时实现两条：

| 路线 | 证据与调用的要求 |
|---|---|
| 先检索、后生成（便于接现有 evidence_id） | 检索取得内容后先登记/冻结证据，再送写作模型；模型只引用输入允许的 ID |
| 模型原生工具检索 | 首次请求冻结研究意图与种子资料；工具结果逐步登记并记录供应商工具事件/来源映射，响应后封存本轮实际证据集。声明引用须能回指该次工具结果，不能只保留最终文字 |

选择后在交付记录写明：能力、协议、工具/适配器、成功与失败证据、哪些来源正文可得、哪些只有摘要。只有 URL 或搜索摘要时就标该层级，不冒充全文核验。没有任何可运行检索路线时只能标部分实现，不能靠模型自己输出一批网址验收“联网”。

当前 `ai_research.py:648–699` 的调用封装主要返回字符串，尚未保留结构化工具事件/usage 等完整结果；采用原生路线需要同步调整封装，不能只加一句“请联网”。本文不要求更换供应商或自动安装浏览器。

**增补验收**：选定路线真实取到一条可核查证据；断网/工具不支持时准确失败或部分成功；引用映射和输入/工具日志保存。原生工具产生的新 ID 不被误当伪造，也不能无限放行任意 ID。

### REV-04：新任务不等于无限重试，也不能承诺供应商绝不重复计费

**第一版位置：§3.1、RES-03。** “同次提交不重复计费”是目标，普通客户端无法单方面保证供应商在超时/进程崩溃时恰好执行一次。应把可验证保证写清楚。

- 本地保证同确认事务性创建一个逻辑任务，正常路径只执行计划内调用；每个供应商请求另有 attempt_id。
- 供应商支持幂等/查询时按其实际能力恢复；不支持时，已经发出但结果未知的调用记录为“结果未知/可能计费”，不自动当未发送再无限重试。
- 只对确定可安全重试的情形做有上限重试；未知结果的再次付费请求按用户既有重试授权/预算决定，缺少相应授权就等待明确决定。
- 每任务明确请求次数/工具次数、超时和输出规模上限；超限停止并记录原因，不静默截断或继续追加收费步骤。不要求为了本轮新建复杂预算页面，现有配置/预览记录足够。
- 输入无效、凭证不可用或关键前置失败时允许在模型前终止；“每次新任务”不能解释成明知无效也必须花一次钱。成功生成的独立投研不得复用旧 AI 结果。

**增补验收**：模拟“供应商已收请求、本地超时”和“收到结果、落盘前崩溃”；恢复不能盲目重发；实际 attempt 和不确定计费不丢失。RES-03 的“不重复计费”按上述可控保证核对，不写成绝对供应商保证。

| REV-07 | 当前快照+新新闻与历史时点研究未完全区分；时效未落到字段 | 新投研默认是“本次知识时点研究”，可引用明确标时的旧行情，但标题/开头不得写成当前价。历史 as-of 模式若已有则严格限定证据可得时间；本轮不强制新建该模式。为行情/技术/新闻分别记录截止时间、时效策略版本和过期原因；新闻旧而仍有效，不以发布日期旧直接判失效。阈值由实际数据频率决定并在交付记录，边界用固定时钟验证 |
| REV-08 | 只说 schema 同步，没明确旧报告/自定义模板的迁移 | B 用新模板/schema 版本；保留旧报告读取分支，不能用 B 强行解析旧结构。未改过的默认 standard 可迁移；用户自定义内容保留并明确其基于版本，提供显式切换/重置，不静默覆盖。用户改正文结构也不能绕过证据底线；UI 显示 B 但实际旧自定义仍生效必须可见。测试旧报告、自定义提示词、B 三种情况 |
| REV-09 | §6“催化是否遗漏”容易被实现成模型或程序已能证明穷尽全网 | 自动校验只保证已定义的结构/覆盖/数字/引用检查；内容是否充分仍有不确定性。分别记录自动通过、内容核验待办、人工核验结果；未人工核验也可供阅读但不冒充人工通过。引用存在不等于来源支持结论，摘要不等于原文，重复转载不等于独立证据；关键冲突保留，普通缺失不一律阻断整个报告 |
| REV-10 | 多币输出不足时易无上限分批，或错把单币成功当整批成功 | 批次冻结目标集合；逐币记录成功/部分/失败与报告版本、分批计数及总 usage。重试只补失败对象，不重新收费生成已成功对象。已成功结果先保留，批次标部分完成；同批恢复仍是原确认，用户另点重新研究才是新确认。报告→草案引用绑定实际单币版本，不因后续报告修订自动改冻结规则 |

REV-07 中的历史 as-of 限制是对已有模式的保护，不扩展为本轮必须开发新历史投研入口。建议六指标放“扫描依据”附件或分布到对应章节，不把市值/净流等全部挤入“合约结构”，保持 B 正文简洁。

## 4. 优化实施顺序，不增加一轮全面重构

1. **先补 R1**：新确认/幂等/数据库约束/两阶段冻结。用离线模拟验证，不需要先真调模型。
2. **把 R2 拆成两个小交付**：R2a 接 B 的结构、实际提示词、旧报告兼容和 UI/导出；R2b 接一条真实检索路线及引用/用量记录。R2a 模拟通过不代表完整投研完成，R2b 未通不能标最新资料已检索。
3. **R3 先验单币标准闭环**：选有明确来源的正常案例，再验一个缺失/冲突案例；真实收费测试按当时授权范围。之后验证多币部分失败与草案接口。STRK 作例子之一，不用一份报告证明所有项目覆盖。
4. **经验库继续后置**：现有文件积累无需通用数据库/反馈平台；可复用的方法先少量试用，跨项目回顾后再决定页面化。

与当前程序不匹配的中间层可以小幅调整，但本轮不需要一次建设通用爬虫平台、全量来源适配器、全新工作流引擎或每步强制额外 AI 核验。先把一条真实路径做完整，同时保留清楚的失败状态。
